# Classic Store — مرجع المشروع الشامل

**الإصدار:** 1.0 — **التاريخ:** 9 نوفمبر 2026  
**الغرض:** مرجع موحّد للمراجعة المعمارية، تنفيذ قاعدة البيانات، تطوير Backend وFrontend، والاختبار.  
**مصادر المحتوى:** الملفات المرفقة في المحادثة فقط؛ أي استنتاج أو توصية خارج نص المصدر موضح بصفته ملاحظة مراجعة.

> **مهم:** ملف SQL المجمع مخصص لقاعدة PostgreSQL جديدة وفارغة. لم يتم تشغيله على PostgreSQL فعلي في بيئة إعداد هذه الملفات؛ لا تعتبره شهادة نجاح تنفيذ.

## 2. نظرة عامة على المنتج

Classic Store متجر B2C لبيع منتجات مادية. النطاق المحدد في SRS الشامل: مصر، العملة EGP، واجهة عربية أساسية مع دعم الإنجليزية، RTL/LTR، مخازن متعددة، اختيار مخزن نشط قريب قادر على تغطية كامل بنود الطلب، وGuest Checkout.

المعمارية المقترحة في SRS: Modular Monolith، Backend باستخدام Spring Boot / Java 21، Frontend باستخدام Next.js / React / TypeScript، وقاعدة PostgreSQL 16+ مع Flyway.

## 4. قاعدة البيانات — ملخص المخطط

- Schema: `store`
- عدد الجداول حسب قاموس البيانات التفصيلي: **32 جدولًا**.
- عدد الأعمدة حسب القاموس التفصيلي: **251 عمودًا**.
- عدد أنواع ENUM المعرفة في SQL الأساسي: **8**.
- قاعدة تسمية قاعدة البيانات: `snake_case`؛ تحويل REST إلى `camelCase` مسؤولية Java mapper.
- الامتدادات المثبتة في SQL: `pgcrypto`, `citext`, `btree_gist`.

### 4.1 أنواع ENUM

- `store.user_role`: CUSTOMER, ADMIN, OPERATIONS, WAREHOUSE, SUPPORT
- `store.product_status`: DRAFT, ACTIVE, ARCHIVED
- `store.order_status`: PENDING, CONFIRMED, PROCESSING, SHIPPED, DELIVERED, CANCELLED, RETURNED
- `store.payment_status`: PENDING, AUTHORIZED, PAID, FAILED, REFUNDED, PARTIALLY_REFUNDED, CANCELLED
- `store.payment_method`: COD, CARD, WALLET, OTHER
- `store.fulfillment_status`: PENDING, ALLOCATED, PICKING, PACKED, DISPATCHED, DELIVERED, CANCELLED
- `store.reservation_status`: ACTIVE, CONSUMED, RELEASED, EXPIRED
- `store.stock_movement_type`: RECEIPT, ADJUSTMENT, RESERVE, RELEASE, SALE, RETURN, TRANSFER_IN, TRANSFER_OUT

### 4.2 فهرس الجداول ووظيفتها

1. `store.countries` — الدول المتاحة في النظام؛ يبدأ المتجر بمصر، ويمكن تفعيل دول أخرى لاحقًا.
2. `store.governorates` — تعريف المحافظات التابعة لكل دولة لاستخدامها في العناوين والتوصيل.
3. `store.cities` — تعريف المدن وربطها بالمحافظات لتحسين إدخال العناوين.
4. `store.users` — حسابات العملاء والموظفين وصلاحياتهم؛ لا يُشترط وجود سجل للزائر.
5. `store.addresses` — دفتر العناوين المحفوظة للعملاء المسجلين؛ لا يعتمد عليه طلب الزائر.
6. `store.settings` — إعدادات المتجر العامة المخزنة في JSON مثل العملة ومدة الحجز.
7. `store.brands` — العلامات التجارية المستخدمة في تصفية المنتجات.
8. `store.categories` — التصنيفات الهرمية لعرض الكتالوج والتنقل.
9. `store.products` — البيانات العامة للمنتج المادي بصرف النظر عن خياراته القابلة للبيع.
10. `store.product_categories` — ربط متعدد إلى متعدد بين المنتجات والتصنيفات.
11. `store.product_variants` — الوحدات الفعلية القابلة للبيع SKU وأسعارها وأبعادها.
12. `store.product_images` — صور المنتج أو متغير محدد وترتيب ظهورها.
13. `store.coupons` — أكواد الخصم وشروط الصلاحية والاستخدام.
14. `store.warehouses` — المخازن ومواقعها الجغرافية؛ تُستخدم في ترتيب الأقرب إلى العميل.
15. `store.inventory` — الرصيد الفعلي والمحجوز لكل متغير داخل كل مخزن.
16. `store.inventory_movements` — دفتر تدقيق لتغيرات المخزون الفعلي والمحجوز.
17. `store.carts` — سلال العملاء المسجلين والزوار قبل تحويلها لطلبات.
18. `store.cart_items` — المتغيرات والكميات المطلوبة في كل سلة.
19. `store.orders` — رأس الطلب وبيانات العميل والمبالغ وعنوان الشحن المثبت لحظة الشراء.
20. `store.order_items` — بنود الطلب مع نسخ ثابتة من أسماء المنتجات والأسعار.
21. `store.order_status_history` — تتبع تغيرات حالة الطلب ومن نفذها ومتى.
22. `store.fulfillments` — عملية تجهيز/شحن طلب من مخزن معين مع بيانات التتبع.
23. `store.fulfillment_items` — البنود والكميات المرتبطة بكل عملية تجهيز.
24. `store.inventory_reservations` — حجز مؤقت للمخزون أثناء إتمام الطلب والدفع.
25. `store.payments` — محاولات/عمليات دفع الطلب سواء إلكترونيًا أو عند الاستلام.
26. `store.payment_events` — أحداث مزود الدفع الواردة (webhooks) للتدقيق ومنع المعالجة المكررة.
27. `store.refunds` — عمليات رد الأموال المرتبطة بمدفوعات سابقة.
28. `store.shipping_zones` — مناطق تغطية الشحن المرتبطة بالدولة أو المحافظة.
29. `store.shipping_rates` — تعريفة الشحن حسب المنطقة وشريحة الوزن.
30. `store.returns` — طلبات إرجاع المنتجات وحالتها.
31. `store.return_items` — المنتجات والكميات المطلوب إرجاعها من طلب سابق.
32. `store.outbox_events` — أحداث الأعمال التي تنتظر النشر إلى أنظمة أخرى بصورة موثوقة.

### 7.2 V7 — Integrity & Reservation Hardening
- حذف القيد الفريد القديم `UNIQUE(order_item_id, warehouse_id)` الذي كان يمنع إنشاء حجز جديد بعد تحرير/انتهاء الحجز السابق.
- فحص وجود مجموعات ACTIVE مكررة قبل إنشاء الفهرس الجديد.
- إنشاء فهرس فريد جزئي على `(order_item_id, warehouse_id)` عندما تكون الحالة `ACTIVE` فقط.
- إضافة Trigger يمنع تعديل/حذف/نقل بند الطلب بعد وجود أي reservation أو fulfillment للطلب.
- إضافة Trigger للتحقق أن fulfillment item تابع لنفس الطلب المرتبط بعملية التجهيز.
- إضافة Trigger للتحقق من تطابق `order_id`, `order_item_id`, `variant_id` في reservation.
- V7 لا تضيف `updated_at` trigger.
- V7 تنص على أن Java service هي المسؤولة عن تنفيذ allocation/reservation، وألا تستدعي دوال allocation القديمة V6.

### 7.3 دورة حالة الحجز
الحالات المعرفة: `ACTIVE`, `CONSUMED`, `RELEASED`, `EXPIRED`. الفهرس الجزئي يسمح بتعدد السجلات التاريخية غير النشطة، ويمنع أكثر من ACTIVE واحد لنفس بند الطلب والمخزن.

**تنبيه:** SQL المرفق لا يحتوي على Scheduled Job يحول الحجوزات المنتهية إلى `EXPIRED` تلقائيًا. قاموس البيانات ينص على ضرورة تحرير الحجوزات المنتهية بمهمة مجدولة؛ تنفيذ هذه المهمة مسؤولية التطبيق/التشغيل ويجب إضافته واختباره.

## 8. قواعد العمل المهمة

- Guest Checkout: `orders.user_id` اختياري، ويقبل الطلب بوجود بيانات اتصال مناسبة؛ جدول `addresses` خاص بالمستخدم المسجل.
- حجز المخزون: `inventory` يحتفظ بالفعلي والمحجوز، و`inventory_reservations` يحتفظ بتفاصيل الحجز وتاريخه.
- اختيار أقرب مخزن: الدالة `store.rank_warehouses` تستخدم مسافة خط مستقيم تقريبية، لا مسافة الطريق. المخزن يجب أن يكون نشطًا وقادرًا على تغطية كل بنود الطلب.
- المنتجات مادية: `products.is_physical` مقيد بأن يكون TRUE.
- ثبات بيانات الطلب: `order_items` يحتفظ بنسخ SKU والاسم والسعر، و`orders` يحتفظ بعنوان الشحن في JSON.
- المدفوعات: `payments` للعملية، و`payment_events` لأحداث المزود، و`refunds` للاستردادات.
- التحقق التطبيقي ضروري لانتقالات الحالات، واتساق المدينة والمحافظة والدولة، ومطابقة إجمالي البنود مع الطلب، وحماية بيانات الدفع.
- الإجمالي المحسوب في SQL: `subtotal - discount_total + shipping_total + tax_total`.

## 9. مراجعة SQL — ملاحظات وتعارضات تحتاج قرارًا

| الأولوية | الموضوع | نتيجة المراجعة |
|---|---|---|
| حرج قبل الإنتاج | تشغيل فعلي | لم يتم تشغيل SQL على PostgreSQL في بيئة الإعداد. يجب تنفيذ الملف على قاعدة فارغة بإصدار PostgreSQL المستهدف، ثم حفظ log ونتيجة الاختبارات. |
| مرتفع | سياسة انتهاء الحجز | لا توجد مهمة مجدولة في SQL لتحويل ACTIVE إلى EXPIRED أو تحرير الحجوزات المنتهية. مطلوب Job/worker موثق مع معالجة آمنة ومتكررة. |
| مرتفع | اختيار المخزن | دوال V6 موجودة، لكن V7 تشترط أن Java service تتولى allocation/reservation وألا تستدعي دوال V6. يجب أن يكون هناك تنفيذ Java فعلي واختبارات تنافسية قبل تفعيل checkout. |
| مرتفع | تطابق المدينة والمحافظة | FK على governorate_id وcity_id منفصلان؛ لا يوجد قيد يثبت أن المدينة تتبع نفس المحافظة المحددة في العنوان/المخزن. قاموس البيانات يحذر من أن هذا تحقق تطبيقي. |
| مرتفع | تطابق الإجمالي | لا يوجد في SQL قيد يطابق مجموع `order_items.line_total` مع `orders.subtotal` أو `grand_total`. يجب أن يحسبها Backend داخل transaction ويتحقق منها. |
| متوسط | حركات المخزون | `inventory_movements` يسجل deltas، لكن SQL لا يفرض قواعد دلالية كاملة على اتجاه كل movement_type أو اتساق delta مع سجل inventory. يلزم توثيق service rules واختبارات. |
| متوسط | الكوبونات | يوجد `usage_limit` و`used_count` لكن لا يوجد CHECK ظاهر يضمن `used_count <= usage_limit` عند وجود حد استخدام؛ يلزم معالجة ذرية في التطبيق أو قيد/آلية معتمدة. |
| متوسط | المرتجعات | FK في `return_items` يربط return وorder_item كلًا على حدة، لكنه لا يثبت أن order_item تابع لنفس order الخاص بالـ return. لا يوجد Trigger مماثل لـ V7 في الملف المرفق. |
| متوسط | تحديث updated_at | القيم الافتراضية تملأ created/updated عند الإدراج، لكنها لا تحدث updated_at تلقائيًا عند كل UPDATE. V7 تعمدت عدم إضافة trigger. |
| متوسط | btree_gist | الامتداد مثبت في SQL لكن لا يظهر استخدام مباشر له في التعريفات المقدمة. لا تحذفه دون قرار، لكن راجع هل مطلوب فعلًا. |
| متوسط | القيود الفريدة للحجوزات | V7 تفترض اسم القيد التلقائي `inventory_reservations_order_item_id_warehouse_id_key`. هذا يطابق التعريف الأصلي المعروض؛ يجب تأكيد الاسم على قاعدة مستهدفة إن كان قد جرى تعديل schema يدويًا. |
| منخفض | قابلية إعادة التشغيل | SQL الأساسي ينشئ الأنواع والجداول دون IF NOT EXISTS؛ الملف المجمع ليس idempotent ولا يعاد تشغيله على قاعدة سبق إنشاؤها. |

## 10. تعليمات إنشاء قاعدة البيانات

- ابدأ بقاعدة PostgreSQL جديدة وفارغة.
- تحقق من نسخة PostgreSQL وصلاحية إنشاء extensions.
- شغّل `Classic_Store_Consolidated_V1-V7.sql` مرة واحدة فقط على القاعدة الفارغة.
- تحقق من وجود schema `store` والجداول الـ32 والأنواع الثمانية والدوال والـ triggers والفهارس.
- تحقق من وجود COMMENT على كل جدول وكل عمود وكل نوع ودالة ضمن النطاق الموثق.
- قارن عدد الأعمدة الفعلي مع قاموس البيانات: 251 عمودًا.
- ولبيئات التطوير/الإنتاج المستمرة، استخدم Flyway migrations المنفصلة والمرتبة بدل الملف المجمع؛ لا تعدّل migrations مطبقة.
- شغّل اختبارات FK/UNIQUE/CHECK، واختبارات الحجز والتحرير والاستهلاك والتزامن وV7.
- ولّد ERD من قاعدة البيانات الفعلية وقارنه بملف ERD المصدر.

## 12. متطلبات التعليقات داخل PostgreSQL

الملف المجمع يضيف `COMMENT ON` للمخطط `store`، والأنواع الثمانية، والجداول الـ32، والأعمدة الـ251، والدوال الثماني، والامتدادات الثلاثة. أوصاف الأعمدة والجداول من قاموس البيانات التفصيلي؛ وصف الدوال والأنواع توثيق وظيفي مستخلص من SQL المصدر.

## 13. متطلبات Backend

- Spring Boot / Java 21 وفق SRS.
- استخدام Flyway لإدارة migrations.
- طبقات Controller/Service/Repository وDTO validation وفق هيكل المشروع المعتمد.
- تحويل أسماء DB snake_case إلى REST camelCase في mapper.
- تنفيذ allocation/reservation في Java service طبقًا لتوجيه V7، مع ترتيب قفل deterministic واختبارات concurrency.
- منع معالجة payment webhook المكرر باستخدام provider_event_id والتحقق من التوقيع.
- Idempotency لعمليات checkout والدفع.
- عدم الثقة في أسعار أو إجماليات أو status أو warehouseId مرسلة من Frontend؛ الخادم يحسبها.
- عدم تخزين بيانات بطاقات حساسة.
- تنفيذ Job لانتهاء الحجوزات وإطلاق outbox events حسب الحاجة.

## 14. متطلبات Frontend

- Next.js / React / TypeScript وفق SRS وFrontend Handoff.
- العربية أولًا مع RTL، والإنجليزية مع LTR.
- استخدام API contract/OpenAPI كمصدر types، وعدم اختراع request/response.
- حالات loading / empty / error / success في كل شاشة.
- عرض المبالغ كنص decimal string بمنزلتين وفق Frontend Handoff، وعدم إجراء حساب نهائي في الواجهة.
- عدم إرسال grandTotal أو order status أو warehouseId في checkout.
- التعامل مع pagination بالشكل الموثق.
- إخفاء عناصر الواجهة حسب الدور لا يغني عن authorization في Backend.
- قرار تخزين access/refresh tokens ما زال مفتوحًا ويحتاج اعتمادًا أمنيًا.
